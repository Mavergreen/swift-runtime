# swift-toolchain 6.3.3-mavericks.1

First release. Publishes the pinned host build environment used by
[Mavergreen/swift-runtime](https://github.com/Mavergreen/swift-runtime) to build a
Swift runtime targeting Mac OS X 10.9.

## Assets

- **`swift-toolchain-6.3.3-mavericks.1-macos-arm64.tar.gz`** (~13 MB) — a *relocatable* CMake
  install tree (CMake package, headers, TableGen binaries) built from swiftlang/llvm-project at
  `82cdc19fa54d566969527b56f587ea8ea30bef51` (branch `swift/release/6.3`).
- **`upstream-swift-6.3.3-RELEASE-osx.pkg`** (~1.5 GB) — a byte-for-byte mirror of the official swift.org
  toolchain installer, kept so builds stay reproducible if swift.org prunes older releases. Its
  SHA256 equals the upstream file's.

## Why this exists

The runtime repo previously built swiftlang's LLVM inside its own CI and cached the result. A
CMake *build tree* bakes absolute paths into `LLVMConfig.cmake` at configure time — notably
`LLVM_CMAKE_DIR`, which points at the LLVM *source* directory. When the repo was renamed the
checkout path moved, the cache key had no path component, and the restored tree pointed at a
directory that no longer existed. Every build failed at configure with:

    Error! LLVMInstallSymlink script must be available.

A CMake *install* tree derives its prefix from the config file's own location, so it cannot fail
this way. Building it once per pin and publishing it also removes an ~8 minute rebuild that was
discarded on every `build.sh` edit and evicted after 7 days.

## Gate

`verify-relocatable.sh` reproduces the original failure mode deliberately: it unpacks the
shipped tarball into a directory whose path differs from where it was built, then runs a full
Swift stdlib-only configure **and** `ninja swiftCore-macosx-x86_64` against it, asserting the
resulting dylib reports `minOS 10.9`. A build tree fails this; an install tree passes.

## Notes

- Host tooling only. Neither asset is redistributed inside the runtime `.pkg`.
- The tarball is not yet byte-reproducible (gzip and tar record mtimes), so rebuilding from
  identical pins yields a different SHA256. Consumers should pin the published hash.
